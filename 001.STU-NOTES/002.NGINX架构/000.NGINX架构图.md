## 0. 一图总览

```
                  ┌──────────┐
                  │  客户端  │
                  └────┬─────┘
                       │ TCP / TLS / HTTP2 / HTTP3(QUIC)
 ══════════════════════╪═══════════ 内核态 ═══════════════════════
                       ▼
     listen socket(s) → 完成队列 → 内核按策略分发给某个 worker
 ══════════════════════════════════════════════════════════════
        │                  │                  │
        ▼                  ▼                  ▼
   ┌──────────┐        ┌──────────┐        ┌──────────┐
   │ worker1  │        │ worker2  │  ...   │ workerN  │    每个 worker:
   │ 事件循环 │        │ 事件循环 │        │ 事件循环 │    单线程 + epoll
   └────┬─────┘        └───┬──────┘        └──┬───────┘    + 红黑树定时器
        │                  │                  │
        └──────── accept → 解析 HTTP → 11阶段流水线 → 过滤链 → 响应
                     (proxy 时走 upstream 非阻塞连接后端)
                                  │
                                  ▼
                    磁盘(sendfile) / 后端服务 / memcached
```

核心思想一句话:**master 只管"生"和"管",worker 单线程用事件驱动扛下全部请求**。

## 1. 进程模型:master-worker

```
main()                                  src/core/nginx.c
 │
 ├─ 解析命令行 / 读 nginx.conf → ngx_init_cycle()
 │     · 编译全部配置,生成各模块 conf_ctx
 │     · ngx_open_listening_sockets():master 统一 bind+listen
 │       (80 等特权端口;reuseport 时为每个 worker 各开一个,见 7.1(C))
 │     · 初始化共享内存(slab 分配器)
 │
 ▼
ngx_master_process_cycle()              src/os/unix/ngx_process_cycle.c:74
 │
 ├─ ngx_start_worker_processes() :336   按 worker_processes fork
 │    │                                 (默认 1;"auto" = ngx_ncpu 即 CPU 核数)
 │    └─ 每个 worker 进入 ngx_worker_process_cycle :699,先做
 │       ngx_worker_process_init() :753:
 │         · setpriority / setrlimit(worker_rlimit_nofile) / CPU 亲和
 │         · 降权到 user 指定的普通用户
 │         · 各模块 init_process:把 listen fd 挂进自己的 epoll
 │
 ├─ ngx_start_cache_manager_processes() fork cache manager / cache loader
 │
 └─ for(;;) sigsuspend()  ← master 平时完全睡眠,醒来只处理信号
       · CHLD → ngx_reap_children():收尸,崩溃的 worker 自动重启
       · QUIT → 通知所有 worker 优雅退出,全部退出后 master 才退出
       · HUP  → 重新读配置建新 cycle → 起新 worker → 旧 worker 优雅退场
       · USR1 → worker 重开日志文件(日志切割)
       · USR2 → 启动新二进制(热升级);WINCH → 优雅退掉旧 worker
```

分工:master(以 root 启动时)负责**绑定特权端口、管理进程树、热加载/热升级**;
worker 以普通用户跑,负责**全部业务**。任何一个 worker 崩溃,master 立刻拉起新的,
不存在"单点线程崩了整个进程组挂掉"的问题。

## 2. Worker 事件循环(高并发的心脏)

```
ngx_worker_process_cycle()                        ngx_process_cycle.c:699
 │
 │  for(;;) ──────────────────────────────────────────────────────┐
 ▼                                                                │
ngx_process_events_and_timers()   src/event/ngx_event.c:195       │
 │                                                                │
 ├─ ① ngx_event_find_timer()                                      │
 │     红黑树里最近的超时还差多久 → 作为本轮 epoll_wait 的 timeout│
 │                                                                │
 ├─ ② accept 竞争(仅 accept_mutex on 时;1.30.2 默认 off)          │
 │      ngx_trylock_accept_mutex():抢共享内存自旋锁               │
 │      抢到   → flags |= NGX_POST_EVENTS,accept 事件先入队       │
 │      没抢到 → 本轮超时压到 accept_mutex_delay(默认 500ms)      │
 │                                                                │
 ├─ ③ ngx_process_events() → ngx_epoll_process_events             │
 │      src/event/modules/ngx_epoll_module.c:784                  │
 │        events = epoll_wait(ep, event_list, nevents, timer)     │
 │      POST_EVENTS 时按事件类型入队,否则当场调 handler:          │
 │        · accept 读事件 → ngx_posted_accept_events(优先)        │
 │        · 其余读写事件  → ngx_posted_events                     │
 │                                                                │
 ├─ ④ ngx_event_process_posted(&ngx_posted_accept_events)         │
 │      先做 accept —— 持锁窗口越短越好                           │
 ├─ ⑤ 若持锁则 ngx_shmtx_unlock()  ← 立刻还锁                     │
 ├─ ⑥ ngx_event_expire_timers()    红黑树里到期的定时器逐个回调   │
 │      (client_header_timeout / keepalive_timeout / 上游超时...) │
 ├─ ⑦ ngx_event_process_posted(&ngx_posted_events)                │
 │      最后处理普通读写事件                                      │
 │                                                                │
 ├─ ngx_terminate → 立即退出        ngx_quit → 关 listen + 空闲   │
 │                                  连接,存量请求处理完再退(优雅) │
 └────────────────────────────────────────────────────────────────┘
```

这个循环就是 worker 的全部:同一时刻**只有一个系统调用在等事件(epoll_wait)**,
其余时间都在干活;成千上万连接共用这一条线程。

## 3. 一次 HTTP 请求的完整生命周期

```
worker 单线程视角,全程无"原地等待",等不到就挂事件让出 CPU
──────────────────────────────────────────────────────────────────
[1] accept          ngx_event_accept.c → ngx_get_connection(s)
    listen 读事件 handler = ngx_http_init_connection   request.c:205
      · 从预分配连接数组取槽位,free_connection_n--
      · rev->handler = ngx_http_wait_request_handler
      · 挂 client_header_timeout 定时器(红黑树,request.c:360)
      · ngx_reusable_connection(c,1):标记为可复用的空闲连接(request.c:361)

[2] 等首个字节      ngx_http_wait_request_handler      request.c:371
    recv() 没数据 → 直接返回,连接只是 epoll 表里的一项,
    不占线程、不占 CPU;数据到了由事件循环再唤醒

[3] 解析            收到数据 → ngx_http_create_request  request.c:533
    rev->handler = ngx_http_process_request_line
      ngx_http_process_request_line        request.c:1109
        └ ngx_http_parse_request_line() 手写状态机(ngx_http_parse.c)
      ngx_http_process_request_headers     request.c:1395
        └ ngx_http_parse_header_line() 逐行解析
    ⚠ 一次 recv 收不完整是常态:状态机记录进度,等下一个读事件续传

[4] 进流水线        ngx_http_process_request           request.c:2098
    · SSL 证书校验等检查后(request.c:2181),连接读写 handler 统一换成
      ngx_http_request_handler —— 后续所有异步事件都从它重入请求处理
    · 调 ngx_http_handler()              core_module.c:841
      → write_event_handler = ngx_http_core_run_phases(:878),
        phase_handler 置于 server_rewrite 起点,启动 11 阶段引擎
    ────────────────► 11 阶段 phase engine(见下节)◄──────────
                       CONTENT 阶段产出响应

[5] 发响应          ngx_http_send_header   core_module.c:1853
                      └ header 过滤链 → 生成状态行+响应头
                    ngx_http_output_filter  core_module.c:1906
                      └ body 过滤链 → writev / sendfile
                    内核缓冲区满(EAGAIN)→ 挂写事件,由事件循环续发

[6] 收尾            ngx_http_finalize_request        request.c:2650
    r->count-- 减到 0 → ngx_http_finalize_connection
      ├─ keepalive:ngx_http_set_keepalive()
      │    连接不关,等 pipelined 或下一个请求 → 回到 [3]
      ├─ 请求体没读完:ngx_http_lingering_close() 慢速丢弃
      └─ 否则 ngx_http_close_request() → 连接槽位归还 free list
──────────────────────────────────────────────────────────────────
```

要点:**解析、业务、发送,每一步都可能被"事件打断再续上"**,
这是理解 NGINX 源码里大量 `handler` 指针换特的钥匙——
handler 换特 = 状态机状态迁移。

## 4. HTTP 处理 11 阶段(phase engine)

配置期 `ngx_http_init_phase_handlers()`(`src/http/ngx_http.c:455`)把 11 个阶段
拍平成一个 handler 数组;请求期 `ngx_http_core_run_phases()`
(`core_module.c:884`)沿 `r->phase_handler` 用 while 循环逐个跑 checker:

```
#  阶段(ngx_http_core_module.h:111)  checker          代表模块/指令
────────────────────────────────────────────────────────────────────────
 0  POST_READ       读完整请求头后    generic      realip(还原真实IP)
 1  SERVER_REWRITE  server 级重写     rewrite      server{} 里的 rewrite/set
 2  FIND_CONFIG     匹配 location     find_config  内置阶段,不可挂自定义
 3  REWRITE         location 级重写   rewrite      location{} 里的 rewrite/set
 4  POST_REWRITE    重写后校验        post_rewrite  URI 变了 → 跳回 2 重新
                                                   匹配;限 10 次防死循环
 5  PREACCESS       访问控制前置      generic      limit_req / limit_conn
 6  ACCESS          访问控制          access       allow/deny / auth_basic /
                                                   auth_request
 7  POST_ACCESS     访问控制后置      post_access  内置阶段
 8  PRECONTENT      产出内容前        generic      try_files / mirror
 9  CONTENT         产生响应          content      static / autoindex /
                                                   proxy / fastcgi / grpc ...
10  LOG             记录访问日志      --           access_log;不进上面数组,
                                                   在请求收尾时调用
                                                   (request.c:3934, 3981)
```

checker 的调用约定(`ngx_http_core_generic_phase`,`core_module.c:906`):

```
handler 返回 NGX_OK        → 跳到 ph->next(跳过本阶段剩余 handler)
handler 返回 NGX_DECLINED  → 本阶段内的下一个 handler
handler 返回 NGX_AGAIN/DONE→ 引擎暂停,等事件驱动再次进入(异步!)
handler 返回错误/HTTP 码   → ngx_http_finalize_request(r, rc) 直接收尾
```

> 想加自己的处理逻辑:确定需求属于哪个阶段(改写头?鉴权?改内容?),
> 在该阶段模块的 `postconfiguration` 里挂 handler 即可——NGINX 二开的标准姿势。

## 5. 响应过滤链(filter chain)

各过滤模块在 `postconfiguration` 里把自己插到链头,组成静态链,
响应流过每个节点后从链尾真正发出:

```
ngx_http_send_header(r)  core_module.c:1853        ── 响应头链 ──
      │
      ▼
ngx_http_top_header_filter                          ngx_http_header_filter
   → not_modified → headers(增删头) → gzip(改头) → ...  (链尾:真正序列化
                                                        状态行 + 响应头)

ngx_http_output_filter(r, chain)  core_module.c:1906  ── 响应体链 ──
      │
      ▼
ngx_http_top_body_filter
   → copy → sub(替换) → gunzip → range → chunked → ... → ngx_http_write_filter
                                                          (链尾:writev/sendfile,
                                                           EAGAIN 时挂写事件)
```

- 链在配置期就串好,运行期零查找开销;
- `ngx_http_write_filter` 是唯一真正碰 `writev/sendfile` 的节点,
  发不完就挂写事件,由事件循环驱动续发——和上面所有"异步续传"是同一套路。

## 6. 反向代理路径(upstream)

```
CONTENT 阶段:proxy_pass / fastcgi_pass / grpc_pass ...
   │  模块给 r 挂上 ngx_http_upstream_t,handler = ngx_http_upstream_init
   ▼
ngx_http_upstream_init                    src/http/ngx_http_upstream.c
   │
   ├─ ① 负载均衡模块选 peer
   │     round-robin(内置默认)/ least_conn / ip_hash / hash / random / sticky
   │     upstream 池状态可放共享内存(zone 指令),跨 worker 共享
   ├─ ② ngx_event_connect_peer() 非阻塞 connect
   │     EINPROGRESS → 等写事件;失败 → 按策略试下一个节点
   ├─ ③ 发请求头/体:客户端 body 边收边转发,事件化流水
   ├─ ④ 收响应:upstream 读事件 → 解析响应头 → 接入下游过滤链发回客户端
   │     proxy_buffering on:先攒进 proxy_buffers,下游按自己节奏慢发
   └─ ⑤ 结束:keepalive 模块把后端连接放回连接池复用
   全程由同一个 worker 事件循环驱动,没有为代理请求单开线程
```

## 7. 高并发方案全景

### 7.1 连接分发:谁来 accept?

`worker_processes = N` 时,所有 worker 都能看见 listen socket,惊群怎么解?

```
(A) 默认:socket sharding(accept_mutex off;1.11.3 起默认,1.30.2 亦然)
    所有 worker 共享同一 listen fd,各自挂进自己的 epoll。
    Linux + epoll + 多 worker 时自动启用 EPOLLEXCLUSIVE
    (NGX_EXCLUSIVE_EVENT,ngx_event.c:926):
      内核只唤醒"一个"worker 处理新连接 → 无惊群
    但 EPOLLEXCLUSIVE 偏爱最先注册的 worker,于是:
      ngx_reorder_accept_events(定义 :450,调用点 :339)
      触发条件(:476):listen 连接 accept 计数到 16 的倍数,或本 worker
      过载(accept_disabled>0)时重挂 socket,让其他 worker 也有机会
      (默认 multi_accept off,一次事件 accept 一个 ≈ 每 16 个连接)

(B) accept_mutex on:共享内存自旋锁 ngx_shmtx
    只有持锁的 worker 把 listen fd 挂进 epoll 去 accept,
    配合 accept_disabled 做"过载让路"(见 7.2)
    代价:同一时刻只有一个 worker 收新连接(老方案)

(C) listen ... reuseport   (解析于 ngx_http_core_module.c:4225)
    配置阶段 ngx_clone_listening(ngx_connection.c:98)按 worker 数克隆
    listening,每份 ls->worker = n(:125);master 为每份各打开一个
    socket(SO_REUSEPORT);worker 只挂 ls->worker == 自己 的那份进
    epoll(ngx_event.c:808);内核按四元组哈希把连接分流到不同 socket
    → 无惊群、无锁、负载最均匀,生产环境推荐

(D) worker_processes 1:无竞争,仅调试用
```

### 7.2 连接数防线

```
worker_connections(默认 512,ngx_event.c:13 DEFAULT_CONNECTIONS)
   → cycle->connection_n:连接数组预分配大小 = 每 worker 并发上限
   ⚠ fd 还要留给 upstream / 日志文件等,需配套 worker_rlimit_nofile

防线①  accept_disabled 自我限流        ngx_event_accept.c:139
    ngx_accept_disabled = connection_n/8 - free_connection_n
    > 0 → 这个 worker"太满了",接下来 disabled 次循环放弃抢 accept 机会
    (新连接自然流向空闲 worker,负载自均衡)

防线②  fd 耗尽兜底                      ngx_event_accept.c:112
    accept() 返回 EMFILE/ENFILE
    → ngx_disable_accept_events():摘掉所有 listen 读事件,然后分两路:
      未开互斥锁 → 挂 accept_mutex_delay(默认500ms)定时器后恢复
      开了互斥锁 → 释放锁 + accept_disabled=1,逐轮递减后再重新抢锁
    两种路径都避免 accept 空转打满 CPU

防线③  应用层限流
    limit_req:漏桶算法(状态放共享内存)  /  limit_conn:并发连接数限制
    都挂在 PREACCESS 阶段,在进入 CONTENT 前就把流量挡掉
```

### 7.3 定时器:一棵红黑树管全部超时

```
ngx_event_timer.c:所有超时统一挂一棵红黑树
  client_header_timeout / keepalive_timeout / proxy_read_timeout /
  limit_req delay ... 全是树上节点

每轮事件循环:
  ngx_event_find_timer() 取最小超时 → epoll_wait(timeout)
    · 因事件提前醒 → 定时器顺延,不浪费
    · 超时醒      → ngx_event_expire_timers() 逐个回调
一次系统调用服务成千上万连接的"心跳",不需要任何 per-connection 定时器
```

### 7.4 posted events:先收事件,后处理

```
为什么要有 posted 队列?(ngx_event_posted.c)
epoll 返回的一批事件若当场逐个处理:
  · 处理过程中可能关闭连接、改动 epoll 注册表 → 后续遍历不可靠
  · accept 与业务事件交织,持锁时间不可控

所以 NGX_POST_EVENTS 时,epoll 循环只把事件挂入三个队列:
  ngx_posted_accept_events ← accept 专用,锁释放前最先处理
  ngx_posted_events        ← 普通读写,释放锁之后再跑
  ngx_posted_next_events   ← 处理中要求"下一轮立刻再跑"的事件
处理中途把 handler 换掉/再入队,就实现了无递归的状态机推进
```

### 7.5 线程池:把阻塞 IO 挪出主线程

```
aio threads(src/core/ngx_thread_pool.c;thread_pool 指令,默认池
32 线程 / max_queue 65536,ngx_thread_pool.c:439-440)

worker 事件循环 ──ngx_thread_task_post──► 任务队列 ─► 线程组(32 线程)
      ▲                                       │ 阻塞型操作:
      │                                       │ 大文件 sendfile 读取等
      │ 完成事件回到 epoll                    ▼
      └───────────────────────────────────完成通知队列
事件循环里绝不阻塞 → 单线程保持吞吐;线程池只是"外挂的阻塞仓库"
```

### 7.6 复用与协议层并发

```
连接/请求复用:
  keepalive_timeout  → 连接处理完不关,省掉 TCP+TLS 握手
  HTTP pipelining    → 一次收下的多个请求排队处理
  upstream keepalive → 对后端也复用连接

协议层并发:
  HTTP/2(src/http/v2)      一条 TLS 连接多路复用流,worker 按事件分帧
  HTTP/3(src/http/v3 + src/event/quic)  单 UDP socket 承载全部流,
                            无传输层队头阻塞、支持连接迁移
```

### 7.7 共享内存与无锁

```
共享内存(ngx_slab.c 分配器)让跨 worker 数据一致:
  · accept_mutex 自旋锁(ngx_shmtx,基于原子 CAS)
  · limit_req / limit_conn 状态、SSL session cache、upstream zone
运行统计:ngx_atomic_fetch_add 无锁累加(stub_status 的 active/accepted)
```

### 高并发小结(答题版)

| 层面 | 手段 |
|---|---|
| 进程 | master-worker 多进程,worker 数≈CPU 核数,崩溃自动拉起 |
| IO 模型 | 单线程 + 非阻塞 + epoll,无每连接线程/栈开销 |
| accept | socket sharding / EPOLLEXCLUSIVE / reuseport / accept_mutex |
| 容量 | connection 数组预分配 + accept_disabled 过载让路 + EMFILE 兜底 |
| 时间 | 红黑树统一定时器,epoll_wait 一次取最近超时 |
| 阻塞 | 线程池外挂阻塞 IO,主循环永不阻塞 |
| 协议 | keepalive / pipelining / HTTP2 多路复用 / HTTP3 QUIC |
| 数据 | 共享内存 slab + 原子操作,无锁统计 |

## 8. master 信号速查

| 信号 | 行为 | 源码标识 |
|---|---|---|
| TERM / INT | 快速关闭 | `NGX_TERMINATE_SIGNAL` |
| QUIT | 优雅关闭(存量请求处理完) | `NGX_SHUTDOWN_SIGNAL` |
| HUP | 重载配置 | `NGX_RECONFIGURE_SIGNAL` |
| USR1 | 重开日志文件 | `NGX_REOPEN_SIGNAL` |

| WINCH | 优雅退掉 worker(配合 USR2) | `NGX_NOACCEPT_SIGNAL` |
| CHLD | master 收尸 / 拉起崩溃 worker | `sigaddset(SIGCHLD)` |
