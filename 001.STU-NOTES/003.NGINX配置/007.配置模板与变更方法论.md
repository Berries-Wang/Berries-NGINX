## 1. 修正版配置模板(1.30.2,注释即出处)

```nginx
# ─── main 块(001 篇)────────────────────────────────────────────
worker_processes auto;                 # nginx.c:1566 → CPU 核数;容器注意 cgroup(:63 sysconf)
worker_cpu_affinity auto;              # nginx.c:1434,配合网卡 RSS;容器慎用
worker_rlimit_nofile 1000000;          # worker 内 setrlimit,ngx_process_cycle.c:777
                                       # 前提:fs.nr_open ≥ 此值

# ─── events 块(001 篇)──────────────────────────────────────────
events {
    use epoll;                         # 冗余(自动选择),写上无害
    worker_connections 65535;          # 默认仅 512!反向代理容量 = 乘积 ÷ 2
    multi_accept off;                  # 默认 off;EPOLLEXCLUSIVE 下开它得不偿失
}                                      # accept_mutex 保持默认 off

# ─── http 块(003/004/006 篇)────────────────────────────────────
http {
    # 数据通路
    sendfile on;                       # 零拷贝,仅本地文件响应
    tcp_nopush on;                     # TCP_CORK,与 sendfile 成对
    tcp_nodelay on;                    # 默认已 on,显式写为声明意图
    open_file_cache max=10000 inactive=60s;   # 省 open+stat
    open_file_cache_valid 60s;
    open_file_cache_min_uses 2;

    # 日志与观测
    log_format timing '$remote_addr [$time_local] "$request" $status '
                      '$request_time $upstream_connect_time '
                      '$upstream_header_time $upstream_response_time';
    access_log /var/log/nginx/access.log timing buffer=32k flush=1s;
    error_log /var/log/nginx/error.log warn;

    # 压缩(004 篇)
    gzip on;
    gzip_comp_level 5;                 # 默认 1;>6 收益趋平
    gzip_min_length 1024;
    gzip_vary on;
    gzip_proxied any;
    gzip_types application/json text/css application/javascript;
                                       # text/html 默认已压,不用写

    # 限流(006 篇)
    limit_req_zone $binary_remote_addr zone=req:10m rate=100r/s;
    limit_conn_zone $binary_remote_addr zone=conn:10m;

    # ─── upstream 块(005 篇)────────────────────────────────────
    upstream backend {
        zone backend_zone 1m;          # 共享后端状态(≠keepalive 连接池)
        keepalive 256;                 # 每 worker 缓存 256 条
                                       # 1.30 起默认已是 32 local,显式写以覆盖
        server 10.0.0.1:8080;
        server 10.0.0.2:8080;
    }

    # ─── server 块(002 篇)──────────────────────────────────────
    server {
        listen 80 reuseport backlog=8192;   # 两头一起调:somaxconn 同步 8192

        location /api/ {
            limit_req zone=req burst=200 nodelay;
            limit_conn conn 20;
            proxy_pass http://backend;
            # 1.30 起 proxy_http_version 默认 1.1、默认不发 Connection 头,
            # keepalive 前提已默认满足(老版本才需要显式配两行)
        }
    }
}
```

对应 sysctl:

```bash
fs.nr_open = 1000000                    # nofile 的绝对天花板
net.core.somaxconn = 8192               # 必须与 listen backlog= 同步调
net.ipv4.tcp_max_syn_backlog = 8192     # 半连接队列,抗 SYN 突发
net.ipv4.ip_local_port_range = 1024 65000
net.ipv4.tcp_tw_reuse = 1               # 只作用于 proxy→upstream 出站方向
```

## 2. 观测证据:改之前先定位,改之后对照

### 客户端视角:curl -w 分层定位

| 字段 | 覆盖时段 | 慢了指向 |
|---|---|---|
| time_namelookup | DNS 解析 | DNS(与 nginx 无关) |
| time_connect | TCP 握手 | 路由 / 半连接队列 |
| time_appconnect | TLS 握手 | 证书链 / 会话复用 |
| time_starttransfer | 到首字节 TTFB | **nginx 排队 + upstream** |
| time_total | 响应收完 | total-TTFB 大 → 传输/响应体/带宽 |

经验读法:`TTFB - appconnect` 才是服务端处理时间;`total - TTFB` 大概率不是 nginx 的事。

### 服务端视角

```
timing 日志   $request_time 高 + $upstream_response_time 低 → 慢在 nginx/客户端侧
              (变量源码见 006 篇)
配置与版本    nginx -T 存档对比 / nginx -V
运行时        /proc/<pid>/limits(fd 四层链验证,001 篇)
              ss -s、ss -tan(established/TIME_WAIT/accept 队列)
错误日志      "worker_connections are not enough" / "too many open files"
              / "worker_connections exceed open file resource limit"(ngx_event.c:519-536)
```

## 3. 变更流程:备份 → 灰度 reload → 验证 → 回滚

```
 备份     cp -a /etc/nginx /etc/nginx.bak.$(date +%F)  +  nginx -T > before.txt
 修改     只改有证据支撑的项,独立成 include 文件,一项一档
 校验     nginx -t(校验到配置合并层,查不出语义不合理)
 灰度     nginx -s reload → 新 worker 用新配置,旧 worker 处理完存量再退场
          (HUP 源码行为见架构笔记第 1/8 节)
 验证     同一批指标、同时间段多次采样对比(§2 的观测项)
 回滚     还原 include → nginx -t → reload;配置独立成文件,回滚 = 删一行 include
```

注意:reload 不断长连接,但**新配置对存量连接不生效**(旧 worker 按旧配置走完
剩余生命周期);SSE / WebSocket 场景要观察存量连接退场时间。

## 4. 参数联动总表:局部正确,整体退化

| 联动对 | 单调一个的后果 | 源码根因 | 详见 |
|---|---|---|---|
| worker_connections ↔ nofile | connections 上去了,fd 中途耗尽 | fd 四层天花板;启动警告 ngx_event.c:519-536 | 001 篇 |
| listen backlog ↔ somaxconn | 只调内核没用,卡在 511 | 生效队列 = min(backlog, somaxconn);NGX_LISTEN_BACKLOG=511 | 002 篇 |
| keepalive_timeout ↔ fd/内存 | 省了握手,空闲连接占满连接槽 | 空闲连接持槽到定时器到点(request.c:3473 挂、:3514 关) | 002 篇 |
| keepalive_timeout ↔ LB 空闲超时 | nginx 长于 LB,LB 踢连接出 RST | nginx 不知道 LB 的空闲策略,需人工保证 nginx < LB | 002 篇 |
| gzip level ↔ CPU/TTFB | 省带宽但 TTFB 变差 | 逐请求在 worker 单线程 deflate(gzip_filter:626) | 004 篇 |
| sendfile ↔ 反向代理 | 代理场景调了无感 | 只对本地文件缓冲生效,代理响应在内存走 writev | 003 篇 |
| tcp_tw_reuse ↔ 入站连接 | 只调内核等不来收益 | 只作用于主动 connect 的出站方向 | 002 篇 |
| upstream keepalive ↔ 后端设置 | nginx 攒连接,后端先踢 | 连接寿命三参数要对齐(keepalive_time/timeout/requests) | 005 篇 |

## 5. 容量估算速查(以 16 worker × 65535 connections 为例)

| 资源 | 估算 | 依据 |
|---|---|---|
| 连接容量(反向代理) | ≈ 52 万(16 × 65535 ÷ 2) | 001 篇双槽模型 |
| fd 需求 | > 105 万(连接 + 日志 + channel) | 001 篇 fd 四层链,fs.nr_open 必须先抬高 |
| 内存 | 数 GB 级:连接骨架(三数组)是小头,请求 pool + 各类缓冲才是大头 | 001 篇 |
| accept 队列 | reuseport 后每 worker 独立队列,各自 min(backlog, somaxconn) | 002 篇 |

方法论一句话:**测量定位 → 证据取证 → 单项变更 → 对照验证 → 可回滚**,
比任何一份参数清单都更接近"从 5 秒到 500ms"。
