## 2. 一条指令是怎么被解析的

配置解析的主链路(全部在 master 启动/重载时执行,worker 不读配置文件):

```
 ngx_init_cycle()                     src/core/ngx_cycle.c
   └─ ngx_conf_parse(&conf, &file)    src/core/ngx_conf_file.c:158
        ├─ ngx_conf_read_token(:503)   逐字符切词:指令名、参数、{} 块边界
        └─ ngx_conf_handler(:356)      查表分派:
              遍历所有模块的 ngx_command_t 指令表,名字匹配 + 上下文合法 → 调 set 回调
```

每条指令在模块里的静态描述(`src/core/ngx_conf_file.h:77`):

```c
struct ngx_command_s {
    ngx_str_t             name;   /* 指令名,如 "worker_connections"      */
    ngx_uint_t            type;   /* 参数个数|所属上下文位标记           */
    char               *(*set)(ngx_conf_t *cf, ngx_command_t *cmd, void *conf);
                                  /* 解析回调:存入模块配置结构           */
    ngx_uint_t            conf;   /* 配置层级偏移(http 模块三级指针用)   */
    ngx_uint_t            offset; /* 直接写入目标结构体的字段偏移        */
    void                 *post;   /* 后处理(如取值范围约束)             */
};
```

**上下文用位标记**,这就是"这条指令能写在哪一层"的源码依据:

```
NGX_MAIN_CONF      src/core/ngx_conf_file.h:51   main 块
NGX_EVENT_CONF     src/event/ngx_event.h:426     events 块
NGX_HTTP_SRV_CONF  src/http/ngx_http_config.h:42 server 块
NGX_HTTP_LOC_CONF  src/http/ngx_http_config.h:43 location 块
(type 字段按位或,如 NGX_HTTP_MAIN_CONF|NGX_HTTP_SRV_CONF|NGX_HTTP_LOC_CONF
 表示三层都能写——绝大多数 http 指令都是这种三连标记)
```

## 3. 嵌套继承:merge 宏三段式

`server` 继承 `http`、`location` 继承 `server` 的机制,不是运行时查表,
而是配置期"逐层拷贝合并":每层 create_conf 时全部置 `NGX_CONF_UNSET`,
再由 merge 宏决定取值顺序(`src/core/ngx_conf_file.h:205`):

```c
#define ngx_conf_merge_value(conf, prev, default)   \
    if (conf == NGX_CONF_UNSET) {                   \
        conf = (prev == NGX_CONF_UNSET) ? default : prev; \
    }
/* 取值优先级:本层写了 → 用本层;没写 → 用上层;上层也没写 → 默认值 */
```

所以笔记里反复出现的"默认值 file:line"都长这样,例如:

```
tcp_nodelay        默认 1      ngx_http_core_module.c:3895  ngx_conf_merge_value(..., 1)
keepalive_timeout  默认 75s    ngx_http_core_module.c:3908  ngx_conf_merge_msec_value(..., 75000)
worker_connections 默认 512    ngx_event.c:1360             ngx_conf_init_uint_value(..., DEFAULT_CONNECTIONS)
```

**配置的三段生命周期**(调试配置问题时的心智模型):

```
① 解析    master:ngx_conf_parse 逐条 set,全部成功才继续
② 合并    master:merge 宏逐层落值(nginx -t 只走到这一步,能查出绝大多数错误)
③ 生效    fork 后各 worker 按合并结果运行;reload = master 重走 ①② 再换 worker
```

> 推论:改配置必须 reload 才生效(信号 HUP,行为见架构笔记第 1/8 节);
> `nginx -t` 校验到合并层,但查不出"值不合理"这类语义问题——那要靠运行期证据(007 篇)。
