## 1. main 块:进程模型三件套

### worker_processes

```
默认 1(nginx.c:1148);auto → ngx_ncpu(nginx.c:1566-1567)
Linux 上 ngx_ncpu = sysconf(_SC_NPROCESSORS_ONLN)   src/os/unix/ngx_posix_init.c:63
⚠ 容器坑:读到的是宿主在线核数,不感知 cgroup CPU 配额 / cpuset;
  容器里要么按配额手写数字,要么验证 ngx_ncpu 与实际可用核一致
```

worker 是单线程事件循环,核数之外多加 worker 只增加切换与竞争(架构笔记第 2 节)。

### worker_cpu_affinity

```
auto 模式:nginx.c:1434 置 cpu_affinity_auto = 1
worker 启动时按序绑核:ngx_process_cycle.c:854-857 → ngx_setaffinity()
收益场景:与网卡 RSS 多队列对齐(同核处理同一条流);
风险场景:容器 / NUMA 上掩码与实际可用核错位,错绑反而有害
```

### worker_rlimit_nofile 与 fd 四层链

worker 初始化时自己调 `setrlimit`,不依赖外部 ulimit:

```c
/* src/os/unix/ngx_process_cycle.c:777-786(ngx_worker_process_init 内) */
if (ccf->rlimit_nofile != NGX_CONF_UNSET) {
    rlmt.rlim_cur = (rlim_t) ccf->rlimit_nofile;
    rlmt.rlim_max = (rlim_t) ccf->rlimit_nofile;
    setrlimit(RLIMIT_NOFILE, &rlmt);      /* 失败仅记 ALERT,不退出 */
}
```

nginx 启动自检会在 connections 超过 rlimit 时警告
(`ngx_event.c:519-536`,`"worker_connections exceed open file resource limit"`):

```
 fs.nr_open(内核绝对上限,默认 1048576)
   ≥ RLIMIT_NOFILE 硬限制
   ≥ nofile 软限制            ← limits.conf(* soft/hard nofile)
                               或 systemd 的 LimitNOFILE=(服务直起时
                               不经过 PAM,limits.conf 不生效)
   ≥ worker_rlimit_nofile     ← nginx.conf,worker 内 setrlimit(:777)
   >  worker_connections + 监听/channel/日志/upstream 的 fd 冗余
```

## 2. events 块:连接容量与收发模式

### worker_connections:默认 512 是离生产默认值最远的参数

每 worker 一套私有连接池,worker 初始化时整块分配(`ngx_event.c:754-775`):
connections / read_events / write_events 三个数组,大小都是 connection_n。

数组里不全是客户端连接——监听 socket 与 master-worker channel 也占槽
(`ngx_event.c:447-452` 校验 `connection_n >= listening 数 + 1`);
反向代理时一个请求同时占 client 槽和 upstream 槽:

```
 静态服务器:一条请求只占 1 个槽
   客户端 ──► [client 槽] ──► worker ──► 磁盘(sendfile,不占连接数组)

 反向代理:一条请求同时占 2 个槽
   客户端 ──► [client 槽] ──► worker ──► [upstream 槽] ──► 后端服务

 容量估算:静态服务器 ≈ worker_processes × worker_connections
          反向代理   ≈ worker_processes × worker_connections ÷ 2
```

内存量级:连接三数组(connections/read/write_events)只是骨架,真正大头是
每请求的 pool、header/body 缓冲与日志缓冲,单连接几 KB 级——
估算容量按"每连接数 KB × 连接数"预留(速查表见 007 篇)。

调多少看证据:error_log 出现 `"worker_connections are not enough"`
(`ngx_event.c:455`)或 ss 看到的 established 接近容量,再加。

### use / multi_accept / accept_mutex

```
use epoll      冗余配置:configure 自动按平台选择,Linux 必是 epoll

               epoll 实例创建(ngx_epoll_module.c:330):
                   ep = epoll_create(cycle->connection_n / 2);
               size 参数是历史 hint,现代内核按需扩容忽略它,÷2 无实际含义

               ET/LT 分工——两类 socket 的注册策略不同:
               · 已连接 socket(accept 后):边沿触发 ET
                     /* ngx_epoll_module.c:701-705 ngx_epoll_add_connection */
                     ee.events = EPOLLIN|EPOLLOUT|EPOLLET|EPOLLRDHUP;
                 一次通知后必须读到 EAGAIN,配合非阻塞 fd 做状态机续传
               · 监听 socket:水平触发 LT;多 worker 时自动加 EPOLLEXCLUSIVE
                 (ngx_event.c:921-926),内核只唤醒一个 worker → 无惊群;
                 内核不允许 EPOLLRDHUP 与 EXCLUSIVE 同用,注册前先清掉
                 (ngx_epoll_module.c:614-618)
                 (完整内核走读见架构笔记 000.NGINX架构图 7.1 节)

multi_accept   默认 off(ngx_event.c:1368)。含义只影响 accept 循环退出条件:
               ngx_event_accept.c:47-49  ev->available = ecf->multi_accept;
               :336  } while (ev->available);
               off → 每次事件 accept 一个(监听 socket 是 LT,不丢连接,worker 天然轮流分担);
               on  → 一次清空 accept 队列,突发时"谁被唤醒谁独吞",worker 间负载不均,
                     且与 EPOLLEXCLUSIVE 的补偿机制(ngx_reorder_accept_events,
                     ngx_event_accept.c:339 调用、:450 定义)相互抵消
               结论:多 worker 场景保持 off

accept_mutex   默认 off(ngx_event.c:1369),显式配置才启用(:649-655)。
               1.11.3 起 EPOLLEXCLUSIVE 接管惊群(架构笔记 7.1),
               老文章"必须开 accept_mutex"的说法已过时
```
